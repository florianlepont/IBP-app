<objective>
Prove the on-device inference pipeline end to end on both platforms, using a stock classifier,
before the fine-tuned model exists — and record what the integration actually cost.

Purpose: this is the one genuinely parallel piece of work in the phase and the one most likely to
burn a day unexpectedly. RESEARCH.md picks `react-native-fast-tflite` plus
`react-native-vision-camera` on the strength of the npm registry and the package-legitimacy gate,
but it could not verify that the pair actually builds against Expo 57 / RN 0.86 on this machine —
and the Android SDK was not even reachable when it looked. Discovering that on measurement day, with
the fine-tuned model in hand and the timebox spent, is the failure this plan exists to prevent.

Running it against a stock ImageNet classifier is deliberate: it separates "the native pipeline
works" from "the fine-tuned model is good", so a failure in either is attributable.

Output: a standalone, gitignored Expo dev-client harness that loads a `.tflite` from an on-device
cache path, runs inference, and emits latency with the device identified.

Timebox discipline (D-19): if the native integration cannot be made to build on both platforms
within roughly half a day, stop and record it. "The recommended runtime does not build on this
stack" is decisive evidence for the ADR, and recording it is the successful outcome — not forcing
it through.
</objective>

  <name>Task 2: Wire the inference screen and prove the pipeline offline with a stock model</name>
  <files>spike/species-recognition/device-harness/App.tsx, spike/species-recognition/device-harness/src/, spike/species-recognition/device-harness/results/</files>
  <action>
    Gate check first. Read `spike/species-recognition/device-harness/GATE`. If its first line reads
    `GATE-HARNESS: BUILD-FAILED`, do not attempt this task: there is no harness to wire a screen
    into. Leave the gate as it stands, make sure the `REASON` line is specific enough for the ADR to
    cite, and stop the plan here. The finding travels to plan 05 and plan 06 through the gate file
    and this plan's SUMMARY. Otherwise proceed.

    Write the minimal harness screen. Minimal is the point — this is a measuring instrument, not a
    feature, and nothing here is carried into Phase 3.

    Model loading, shaped by D-07. The model is downloaded separately on first launch and is not
    bundled in the binary, so the harness must load the `.tflite` from an on-device cache path via
    `expo-file-system`, not from `require()` of a bundled asset. RESEARCH.md's loading example shows
    the `loadTensorflowModel({ url })` form that takes a local path — use that shape. Measuring a
    bundled model would measure a distribution mechanism the product has already ruled out. Fix the
    cache path and its file-naming convention now and record it in the harness README: plan 05 drops
    the fine-tuned model into that exact path, and a mismatch stalls measurement day.

    Missing-model behaviour, per D-08. When no model file is present at the cache path, or loading
    fails, the screen must show an explicit message saying recognition is unavailable and remain
    usable. Silent failure was rejected in D-08 because the ecologist would conclude the feature is
    broken. Proving this path works in the harness is what lets the ADR state the behaviour as
    implemented-and-checked rather than as an intention.

    Inference and timing. Load the model once and keep it, then run inference on a fixed test image
    bundled with the harness so runs are comparable. Time only the inference call, the way
    RESEARCH.md's example brackets `model.run` — but also record, separately, the preprocessing time
    to resize and normalise the image into the input tensor, because D-05's three-second budget is
    wall-clock from the ecologist's point of view and RESEARCH.md's Don't Hand-Roll table warns that
    JS-side pixel work can consume the budget before inference starts. Run the same image N times
    and report median and worst case, not a single sample; one run on a cold model measures process
    startup, not inference.

    Offline proof, per D-06. Inference is on-device only, with no server inference and no network
    fallback, because the photo is taken in a forest with no signal and offline-first is a locked
    ADR-001 decision. Have the harness run its inference pass with the device in airplane mode and
    record that it did. This is the cheapest possible proof of the phase's central architectural
    claim, and it also satisfies criterion 4 of the ROADMAP goal by construction: no inference
    crosses the network, so no recurring inference cost can arise.

    Photo handling, per D-13. The recognition photo is transient and not kept. Hold the frame in
    memory and let it go — do not write the captured image to disk, to a cache directory, or to a
    log, not even temporarily for debugging. RESEARCH.md's security section names this precisely:
    the spike must not establish a pattern of writing the photo to disk that then gets carried into
    Phase 3.

    Result record. Emit one line per run into `device-harness/results/` as CSV with: timestamp,
    device model, OS version, model file name, model file size in bytes, preprocessing milliseconds,
    inference milliseconds, and the top-3 label indices with their scores. The device model and OS
    version are not optional — RESEARCH.md Pitfall 4 records that a latency number without a device
    attached is not a measurement. CSV rather than JSON keeps the file outside the root
    `format:check` glob if it is ever moved out of the ignored tree.

    Prove it with a stock model. Fetch a stock quantised MobileNetV3 or MobileNet ImageNet
    classifier in `.tflite` form, place it at the cache path, and run the harness on a real iOS
    device and a real Android device. This is a pipeline proof, not evidence: its accuracy is
    meaningless for this phase because it classifies ImageNet categories, not CNPF genera. Record
    its latency anyway as a sanity reading against RESEARCH.md's assumption A1, which guesses low
    single-digit megabytes and tens of milliseconds and explicitly asks the spike to verify rather
    than inherit it.

    Gate file, final write. Once the stock model has run on both handsets, confirm the first line of
    `spike/species-recognition/device-harness/GATE` reads `GATE-HARNESS: PASS`. If either platform
    could not be run at all, set it to `GATE-HARNESS: BUILD-FAILED` with the reason — a harness that
    runs on only one platform cannot satisfy ROADMAP criterion 2, and plan 05 must know that before
    it schedules a measurement day rather than after. Keep the `RUNTIME`, `RUNTIME-SUBSTITUTION` and
    `REASON` lines accurate to what was actually used.

    This harness is throwaway. It does not need, and must not be held to, the project's test, lint,
    type-check or Prettier standards — plan 01 put `spike/` into `.prettierignore` for that reason.
    Do not add a test file, an ESLint config or a `tsconfig` strictness pass to it.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm → harness | Native module code from `react-native-fast-tflite` and `react-native-vision-camera` compiles into and runs inside a signed build on a personal device |
| public internet → device | The stock `.tflite` classifier is fetched from a third-party host and loaded directly into the inference runtime |
| camera → device storage | A captured frame could be persisted in violation of D-13 if the harness writes it anywhere |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-SC | Tampering | npm install of `react-native-fast-tflite` and `react-native-vision-camera` into the harness | medium | mitigate | Both are OK/Approved in RESEARCH.md's Package Legitimacy Audit, verified live against the npm registry on 2026-09-22, MIT, no postinstall script. `react-native-executorch` is SUS and is deliberately not used, so no legitimacy checkpoint is required in this plan — task 1's automated gate fails the build if it appears |
| T-01-07 | Tampering | The stock `.tflite` file is untrusted input to a native inference runtime | medium | mitigate | Fetch over HTTPS from an official TensorFlow / Kaggle Models endpoint, record the URL and the file hash in the harness results; the harness fails closed to D-08's explicit unavailable message on a load error rather than crashing — the same control the ADR will require of Phase 3's download path |
| T-01-08 | Information Disclosure | Captured recognition frame written to disk, cache or logs against D-13 | medium | mitigate | The harness holds the frame in memory only and writes no image anywhere, including for debugging; the CSV record carries timings and label indices, never image data or a file path to one |
| T-01-09 | Spoofing | Sideloading an unsigned development build onto a personal handset | low | accept | Standard Expo dev-client workflow on a developer-owned device, removed after the spike; no production credential, no store distribution, no user data involved |
</threat_model>
