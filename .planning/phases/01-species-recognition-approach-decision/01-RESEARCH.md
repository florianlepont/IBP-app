## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Recognition targets the **genus only**, never the species. Factor A counts native
  genera from the closed CNPF regional list (`docs/specs/ibp-form-spec.md` §Factor A), so genus is
  both what the score needs and a far more tractable classification problem.
- **D-02:** The bar for "it works" is **the correct genus among the top 3 most likely, 95% of the
  time**. This is an *evaluation* metric, not a screen design — see D-07 (below, renumbered D-11 in original).
- **D-03:** Accuracy must be reported **per genus, never as a single average**. Without a
  per-genus breakdown, rare genera drag the average down and hide the fact that frequent genera
  work. The partial-go rule (D-04) is unusable without this breakdown.
- **D-04:** If results are mixed, the decision rule is a **partial go**: enable suggestions only
  for genera that clear the bar, keep manual entry for the rest.
- **D-05:** Inference must complete in **under 3 seconds** on the measured devices.
- **D-06:** **On-device only.** No server inference, no network fallback. Offline-first is a
  LOCKED ADR-001 decision (DEC-006) and the photo is taken in a forest with no signal. This also
  satisfies the phase's no-recurring-cost criterion by construction.
- **D-07:** The model is **downloaded separately on first launch**, not bundled in the binary.
  Cost: the app must handle a "model not present yet" state (D-08).
- **D-08:** When the model is unavailable — not yet downloaded, or a load failure — the app shows
  an **explicit message and falls back to normal manual entry**. Silent fallback was rejected.
- **D-09:** The model licence must be **permissive and redistributable**. The association is a
  non-profit with a near-zero budget and the app ships on public stores.
- **D-10:** **Both photo subjects are to be measured**: a single subject (one tree, a leaf or
  bark close-up) *and* a stand photo containing several trees. The stand case requires detection
  before classification and is materially harder — it is the scenario most likely to drive a
  no-go. The ADR decides on the measured figures rather than on intuition.
- **D-11:** The screen shows the **most likely genus first with its confidence**, with the
  remaining candidates listed underneath — not three genera presented as equal options.
- **D-12:** Confidence is shown **in plain words — strong / medium / weak**, not as a percentage.
- **D-13:** The recognition photo is **transient and not kept**. It does not consume the
  10-photo survey attachment quota, costs no storage or sync, and requires no data-contract
  extension.
- **D-14:** The ecologist's corrections of wrong suggestions are **not captured** in this
  milestone. See Deferred Ideas.
- **D-15:** **The genus list must be introduced.** The shipped app stores Factor A as a single
  number (`native_genus_count`); the spec calls for a multi-select of observed native genera with
  a derived counter. Recognition produces a genus name and the form has nowhere to put it today
  — even a perfect model delivers nothing as things stand. This is Phase 2's bulk of work; the
  ADR must record it as a precondition of US-C9.
- **D-16:** Accuracy is measured on **public labelled tree-image datasets first, then validated
  on field photographs**.
- **D-17:** Measurement covers the **whole CNPF regional genus list**, reported per genus (D-03).
- **D-18:** Latency is measured on the **observers' real phones**. *Open item for the spike:
  establish which phones the association's observers actually use.*
- **D-19:** The spike is **timeboxed to two or three days**.

### Claude's Discretion

- Choice of inference runtime (Core ML, TensorFlow Lite, ONNX Runtime, ExecuTorch or another) and
  of the candidate models to measure — constrained by D-06, D-07 and D-09.
- How the throwaway spike is structured, and whether it runs inside the Expo app via a dev client
  or as a standalone harness. Native modules are available: `ios/` and `android/` are generated by
  `expo prebuild` (see `mobile/README-native.md`).
- The exact ADR file name and numbering, following the ADR-001 precedent.
- Which public datasets to use, subject to D-09's licence constraint applying to data as well.

### Deferred Ideas (OUT OF SCOPE)

- **Capturing the ecologist's corrections of wrong suggestions** to build an improvement dataset.
  Needs storage, a GDPR position and a retraining story — belongs to a later milestone.
- **Species-level identification** (beyond genus). D-01 scopes this phase to genus. Species could
  serve future uses (rare-species gamification in US-F5) but that is next-milestone territory.
- **Server-side recognition for archived photos.** Rejected here by D-06 for field use; a server
  pass over already-synced photos is a different capability, revisitable once the app is no
  longer internal-only.

## Summary

The runtime question has a clear, low-risk answer: **`react-native-fast-tflite`** (MIT, mrousavy, actively maintained, 15.5k weekly downloads) paired with **`react-native-vision-camera`** (MIT, same author, 425k weekly downloads) is the standard, well-trodden way to run a TensorFlow Lite classifier on-device in an Expo-prebuild app today. It works with Expo 57 / RN 0.86 through a config plugin and `expo prebuild`, exactly the pattern `mobile/README-native.md` already documents for this repo. `onnxruntime-react-native` (MIT, Microsoft) is a credible second choice if a PyTorch-trained model is easier to export to ONNX than to TFLite. `react-native-executorch` (MIT, Software Mansion) is real and well-built but is version 0.10 published days before this research and is flagged suspicious by the package-legitimacy gate on recency grounds alone — it is a reasonable fallback, not the default pick for a 2–3 day spike.

The model question has no shortcut: **no pretrained, permissively-licensed, tree-genus classifier exists off the shelf.** Nothing found in this research — not Pl@ntNet, not PlantCLEF, not any Hugging Face plant model — ships a ready model restricted to the ~33-genus CNPF list with a licence clear enough to redistribute in a public app. The realistic path is transfer learning: fine-tune an ImageNet-pretrained mobile backbone (MobileNetV3-Small or EfficientNet-Lite0, both Apache-2.0 architectures with no data-licence entanglement) on a permissively-licensed image set filtered to the CNPF genera, then convert to `.tflite`. This is a 1-day task for someone comfortable with a basic PyTorch/Keras transfer-learning script, which fits inside the spike's timebox for the single-subject case only.

The stand-photo case (D-10) is the one most likely to produce a no-go, and this research found nothing to contradict that expectation. Ground-level multi-tree detection is a niche research problem: the closest published datasets (SilvaScenes — Quebec, non-European species, unconfirmed licence; ForTrunkDet — CC-BY but only two species, Eucalyptus and Pinus) do not cover the CNPF genus list and are not proven ready-to-use models. Building and validating a custom trunk detector from scratch is a multi-week research effort on its own, not a 2–3 day spike task. The honest recommendation is to spend the spike's budget on the single-subject case, measure the stand case with whatever time remains (even a naive whole-image classification run without detection, clearly labelled as informal), and let the ADR state plainly that the stand case is unproven and likely out of scope for this milestone.

The CNPF genus list itself was not previously available in the codebase (D-15's "discovered gap") but **is publicly reproducible from the official IBP FR v3.2 methodology PDF** (`cnpf.fr`, dated 2026-02-02) — its Factor A table lists 33 genera (34 counting the mandatory Quercus deciduous/evergreen split) with Latin binomials. This is the classification target set, and 33–34 classes is a tractable, closed-set problem — far more achievable than open-set species identification. The one caveat: the repository's own reference documents (`docs/references/README.md`, `docs/specs/ibp-form-spec.md`) cite **IBP Fr v3.0**, while CNPF's currently published document is **v3.2**. This version drift predates this phase and should be flagged, not silently resolved, in the ADR.

**Primary recommendation:** Spike with `react-native-fast-tflite` + `react-native-vision-camera`, a MobileNetV3-Small backbone fine-tuned on a Pl@ntNet-300K/GBIF-sourced subset filtered to the CNPF genus list, measured on real iOS and Android hardware for the single-subject case; treat the stand-photo case as a likely no-go and say so with evidence rather than force a result.

### Pattern 1: On-device classification via TFLite + VisionCamera
**What:** Capture a frame or photo, resize/normalize it to the model's expected input tensor, run inference synchronously via `react-native-fast-tflite`, softmax the output, sort by confidence.
**When to use:** Single-subject photo case (leaf/bark/whole-tree close-up) — this is the tractable case.
**Example:**
```typescript
// Source: react-native-fast-tflite README pattern, github.com/mrousavy/react-native-fast-tflite
import { loadTensorflowModel } from 'react-native-fast-tflite'

const model = await loadTensorflowModel(require('./genus_classifier.tflite'))
const output = await model.run([preprocessedImageTensor])
const genusProbabilities = softmax(output[0])
const topCandidates = argsortDescending(genusProbabilities).slice(0, 3)
```

### Pattern 2: Config-plugin native module install under `expo prebuild`
**What:** Declare the native module in `app.json`'s `plugins` array so `expo prebuild` wires it into the generated `ios/`/`android/` projects, rather than hand-editing generated files.
**When to use:** Any native inference runtime in this repo, per `mobile/README-native.md`'s established convention.
**Example:**
```json
{
  "expo": {
    "plugins": [
      ["react-native-fast-tflite", { "enableAndroidGpuLibraries": ["libOpenCL-pixel.so", "libGLES_mali.so"] }],
      "react-native-vision-camera"
    ]
  }
}
```

### Anti-Patterns to Avoid
- **Bundling the model in the app binary:** Violates D-07 directly; also bloats store download size for a feature that may be a no-go.
- **Silent fallback to manual entry:** Violates D-08; the ecologist must see an explicit message when the model is unavailable, not a feature that quietly does nothing.
- **Training/measuring on a species-level target:** Violates D-01; genus is the target, and conflating the two invalidates every accuracy figure the spike produces.
- **Averaging accuracy across genera into one number:** Violates D-03/D-17; a single average hides which genera actually clear the bar and makes the partial-go rule (D-04) impossible to apply.
- **Treating the stand-photo case as "run the classifier on the whole image":** Produces a number, but not one that answers the real question (which of several trees got which label) — if this shortcut is taken under time pressure, the ADR must label the resulting figure as informal/non-representative, not as evidence for a stand-case go.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| TFLite model execution + hardware acceleration | A custom native bridge to TensorFlow Lite's C++ API | `react-native-fast-tflite` | GPU/NNAPI/Core ML delegate wiring, buffer marshalling and JSI bindings are already solved and maintained; reinventing this is weeks of native code for zero product value |
| Camera frame capture and buffer access | A custom native camera module | `react-native-vision-camera` | Handles both platforms' camera APIs, permission flows and frame-processor plumbing; this is exactly the kind of infrastructure code the "don't hand-roll" principle exists for |
| Image resize/normalize to tensor | Hand-written pixel-loop resizing in JS | Native resize via VisionCamera's frame processor or a small native image-processing step bundled with the TFLite plugin | JS-side pixel manipulation is slow enough to blow the 3-second latency budget (D-05) on its own before inference even starts |
| Ground-level multi-tree object detection | A custom-trained trunk detector, built from scratch in the spike | Nothing off-the-shelf is production-ready for this (see Common Pitfalls) — the honest move is to not build it in 2–3 days, not to hand-roll a rushed, unvalidated one | A rushed detector produces a number that looks like evidence but isn't; better to report "not attempted, here's why" than a fabricated pass |

**Key insight:** Every piece of infrastructure in this domain (camera access, tensor execution, hardware delegates) already has a mature, permissively-licensed library. The genuinely hard, unsolved part is the model and the stand-photo detection problem — and no library shortcuts that; it requires real data work within the timebox, which is exactly why this phase exists as a measurement exercise rather than an integration task.

## Common Pitfalls

### Pitfall 1: Assuming a pretrained "tree species" model exists and is licence-clean
**What goes wrong:** Teams search for "tree species classifier tflite," find something on Hugging Face or Kaggle Models, and ship it without checking the training data's licence — which is very often iNaturalist images with a `CC-BY-NC` (non-commercial) restriction baked in, incompatible with a public app even if the app itself is free/non-profit revenue-generating in any way (donations count).
**Why it happens:** Model *cards* rarely audit their *training data's* licence chain; a model itself being "open" (weights downloadable) says nothing about whether the underlying photos were licensed for this use.
**How to avoid:** Trace every candidate model back to its training dataset's stated licence, not just the model repository's licence badge. This research found no fully clean pretrained tree-genus model — expect to fine-tune, not download-and-ship.
**Warning signs:** A model card that doesn't name its training dataset, or names iNaturalist/GBIF without specifying the licence filter applied.

### Pitfall 2: Conflating species-level and genus-level accuracy
**What goes wrong:** Public benchmarks (PlantCLEF, Pl@ntNet-300K) report species-level top-1/top-5 accuracy on hundreds to thousands of classes. Reusing those published numbers as a proxy for "this will work for genus classification" is invalid — genus classification is a strictly easier, smaller-class-count problem, and reusing species-level pessimism (or optimism) without re-measuring at genus granularity produces a misleading go/no-go input.
**Why it happens:** It's tempting to cite an existing paper's number instead of running the spike's own evaluation.
**How to avoid:** D-16 already mandates measuring on public datasets first, then field photos — the spike must aggregate species-level datasets *up* to genus labels before computing accuracy, and only cite the spike's own genus-level numbers in the ADR.
**Warning signs:** An ADR draft that cites a paper's species-level accuracy figure as if it were a genus-level figure.

### Pitfall 3: The stand-photo case silently becomes "whichever tree is biggest in frame"
**What goes wrong:** Without an explicit detection step, a whole-image classifier trained on single-subject crops will just respond to whatever dominates the frame (usually the nearest or largest trunk), giving a plausible-looking but meaningless answer for a photo containing several different genera.
**Why it happens:** It's the path of least resistance under a 2–3 day timebox, and the model doesn't fail loudly — it just answers confidently and wrongly.
**How to avoid:** Either build a minimal detection step (crop candidate regions, classify each) or explicitly label whole-image-on-a-stand-photo results as "not a valid measurement of the stand case" in the spike's output and the ADR.
**Warning signs:** Stand-case accuracy numbers that look suspiciously close to single-subject numbers — a red flag that no real detection happened.

### Pitfall 4: Measuring latency on a development machine's simulator, not real hardware
**What goes wrong:** iOS Simulator and Android Emulator run inference on the host machine's CPU/GPU (a laptop), which is dramatically faster than a mid-range field phone — a latency figure from the simulator can look well under the 3s budget (D-05) while the real device blows past it.
**Why it happens:** Simulators are faster to iterate with during development.
**How to avoid:** D-18 already locks this — real iOS and real Android hardware, and per the open item in CONTEXT.md, find out which phones the association's observers actually carry before picking test devices; a flagship test phone can hide a real-world failure just as badly as a simulator.
**Warning signs:** Latency numbers reported without a specific device model and OS version attached.

### Pitfall 5: `expo prebuild --clean` wiping a manually-tweaked native integration mid-spike
**What goes wrong:** `mobile/README-native.md` already documents this exact failure mode for this repo — editing `ios/`/`android/` directly instead of `app.json`/a config plugin works until the next prebuild, then silently vanishes.
**Why it happens:** Under spike time pressure it's tempting to hand-patch a native project to get something working quickly.
**How to avoid:** Even in throwaway spike code, express native changes through the config-plugin pattern this repo already uses — it's not meaningfully slower and avoids losing the day's work to an accidental `prebuild --clean`.
**Warning signs:** Native integration that "was working yesterday" and isn't today with no code change in `app.json` or `mobile/plugins/`.

## Code Examples

### Loading and running a TFLite model
```typescript
// Source: react-native-fast-tflite README pattern (github.com/mrousavy/react-native-fast-tflite)
import { loadTensorflowModel, TensorflowModel } from 'react-native-fast-tflite'

let model: TensorflowModel | undefined

async function ensureModelLoaded(localModelPath: string) {
  if (!model) {
    model = await loadTensorflowModel({ url: localModelPath })
  }
  return model
}

async function classify(inputTensor: Float32Array) {
  const loaded = await ensureModelLoaded(cachedModelPath)
  const start = performance.now()
  const outputs = await loaded.run([inputTensor])
  const latencyMs = performance.now() - start
  return { outputs, latencyMs }
}
```

### Top-3 per-genus accuracy computation (evaluation harness)
```python
# Standard scikit-learn top-k pattern — no external citation needed, well-established practice
import numpy as np

def top_k_accuracy_per_class(y_true, y_prob, class_names, k=3):
    top_k_preds = np.argsort(-y_prob, axis=1)[:, :k]
    results = {}
    for class_idx, class_name in enumerate(class_names):
        mask = y_true == class_idx
        if mask.sum() == 0:
            results[class_name] = None  # no test examples for this genus — must be reported, not silently dropped
            continue
        hits = np.any(top_k_preds[mask] == class_idx, axis=1)
        results[class_name] = hits.mean()
    return results
```
This is the shape D-03's "per genus, never a single average" requirement demands — note the explicit `None` for zero-sample genera rather than silently excluding them from the report.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|---------------|-------------------|---------------|--------|
| Bridge-based RN native modules for ML (slow JS↔native serialization) | JSI-based libraries (`react-native-fast-tflite`, `react-native-vision-camera`) with direct memory access | Ongoing since RN's New Architecture rollout, now the default expectation | Enables real-time frame-processor inference without the old bridge's serialization overhead — relevant to hitting the 3s latency budget |
| Hand-picking TFLite vs Core ML vs NNAPI per platform | Cross-platform wrappers (`fast-tflite`, ExecuTorch) that pick the right on-device delegate per platform automatically | Recent (ExecuTorch is a 2025-era PyTorch Foundation project) | Fewer platform-specific code paths for a 2–3 day spike to maintain |
| Full ResNet/VGG-class classifiers on mobile | Purpose-built mobile architectures (MobileNetV3, EfficientNet-Lite) with quantization-aware training | Well-established (MobileNetV3 paper, 2019; EfficientNet-Lite, 2020) but still the current standard for on-device classification | Keeps model size in the low single-digit MB and inference in the tens-of-milliseconds range, both well inside this phase's budgets |

**Deprecated/outdated:** Older RN ML bridges (e.g. `tensorflow/tfjs-react-native`, which runs inference in JS via WebGL rather than native code) are markedly slower and not recommended for a 3-second-latency-budget use case — not researched further given `fast-tflite`'s clear advantage.

## Open Questions

1. **Which document version is authoritative: IBP Fr v3.0 (cited in this repo) or IBP FR v3.2 (currently published by CNPF, dated 2026-02-02)?**
   - What we know: `docs/references/README.md` and `docs/specs/ibp-form-spec.md` cite "IBP Fr v3.0". The document actually live at CNPF's own published URL today (`cnpf.fr/sites/socle/files/2026-04/IBP_FR_v3_2_260202.pdf`) is v3.2, dated 2026-02-02, and its Factor A genus table differs in small ways from what might be assumed from an older version (e.g., the exact "essences supplémentaires cas 4 et 2" set).
   - What's unclear: Whether the association deliberately pinned to v3.0's rules for consistency with prior survey data, or whether this is simply undiscovered document drift (in the same vein as the other stale-doc findings already logged in `.planning/INGEST-CONFLICTS.md`).
   - Recommendation: Flag this explicitly in the ADR as a discovered-but-out-of-scope finding for Phase 1 (this phase only needs *a* genus list to measure against, and v3.2's 33–34 genera is a defensible, sourced choice); let Phase 2 (which owns the data model / genus list entity, D-15) formally decide which version the app follows.

2. **What phones do the association's observers actually carry?**
   - What we know: D-18 requires measuring latency on real iOS and real Android hardware; nothing in the codebase or planning docs names specific device models.
   - What's unclear: Whether "real device" means the developer's own phone (likely a recent flagship) or genuinely representative field hardware (possibly older/mid-range).
   - Recommendation: This is explicitly called out in CONTEXT.md as "Open item for the spike" — the spike's task list (owned by the planner) should include a step to ask the association or check prior field-test reports (`docs/user-tests/`) for device models before finalizing which two devices to benchmark on.

3. **Is a detection step for the stand-photo case worth even a partial attempt within the timebox, or should the spike explicitly skip it?**
   - What we know: No off-the-shelf, licence-clean, CNPF-genus-scoped detector exists (see Common Pitfalls). Building one from scratch is a multi-week effort.
   - What's unclear: Whether a *crude* fallback (e.g., a generic "trunk-like vertical object" heuristic, or manually cropping multiple regions in a handful of test photos to at least produce a directional number) is worth the spike's limited time, versus spending that time getting the single-subject case as solid as possible.
   - Recommendation: Default to the latter — solidify the single-subject measurement first; only attempt a crude stand-photo pass with whatever time is left, and label its output as directional/non-representative in the ADR rather than as a real accuracy figure.

## Security Domain

This phase introduces a first-launch, unauthenticated file download (the model artifact) and on-device inference over user-captured photos that are never persisted or transmitted (D-13). The blast radius is small, but not zero.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|----------------|---------|--------------------|
| V2 Authentication | No | Model download is a public, unauthenticated asset fetch — no user credentials involved |
| V3 Session Management | No | Not applicable to this phase |
| V4 Access Control | No | The model file is a public asset by design (D-07); no access control needed beyond normal object-storage hygiene |
| V5 Input Validation | Yes | The downloaded model file itself is untrusted input to the TFLite/ONNX runtime — validate its checksum/size against a known-good manifest before loading, and handle load failures per D-08 (explicit message, fallback to manual entry) rather than crashing |
| V6 Cryptography | Marginal | No new cryptographic material introduced; rely on TLS for the download (standard, already project-wide per ADR-001) |
| V9 Communications Security | Yes | The model download must happen over HTTPS (the existing object-storage endpoint already serves attachments over TLS, per `CLAUDE.md`'s `OBJECT_STORAGE_ENDPOINT` convention) — no new infrastructure needed, just confirm the model-serving path reuses the same TLS-terminated endpoint |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| Malicious/corrupted model file served from compromised or misconfigured object storage | Tampering | Checksum/hash verification of the downloaded model file against a manifest value before loading it into the inference runtime; fail closed to D-08's explicit-message fallback on mismatch |
| Recognition photo inadvertently retained or logged despite D-13's "transient, not kept" requirement | Information Disclosure | Ensure the recognition photo buffer is not written to `local_attachments` or any persistent cache path — this is a code-review concern for Phase 3, but the spike itself must not accidentally establish a bad pattern (e.g., writing the photo to disk "for debugging" and leaving it in the throwaway harness's shipped defaults) |
