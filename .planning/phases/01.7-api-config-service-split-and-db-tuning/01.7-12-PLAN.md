The "re-read under lock → same-version classify" block exists three times (create race, and twice in the update path): it becomes one private helper.
Design (RESEARCH Pattern 4, SQL verified on PG16; adapted so both paths stay within budget):
1. Statement A, always: unlocked `readForUpsert(db, id, userId)` → `SELECT s.*, s.xmin::text AS cas_token, COALESCE((SELECT array_agg(parcel_id ORDER BY parcel_id) FROM survey_parcels WHERE survey_id = s.id), '{}') AS parcel_ids FROM surveys s WHERE s.id = $1 AND s.user_id = $2`. No row for this user → create path; row → JS decisions exactly as today (older version 409, same-version classification, submitted read-only).
2. Create path, statement B: `createSurveyAtomic(db, input)` = one writable CTE: `input_parcels` (unnest of the normalised ids with their commune/section/number, same derivation as ParcelsService.ensureParcelIds) → `ensured` (`INSERT INTO parcels … ON CONFLICT (parcel_id) DO NOTHING`) → `ins` (`INSERT INTO surveys … ON CONFLICT (id) DO NOTHING RETURNING id, updated_at::text`, with observation_year / version_number / previous_survey_id computed by scalar subqueries that replicate resolveVersionInfo and getDefaultVersionNumber exactly) → `links` (`INSERT INTO survey_parcels SELECT ins.id, … FROM ins CROSS JOIN input_parcels`) → `ev` (`SURVEY_EVENT_INSERT_SQL SELECT gen_random_uuid()/…, ins.id, $user, 'created', $payload::jsonb FROM ins`) → `SELECT * FROM ins`. 0 rows (id exists: concurrent create or another user's id) → `upsertLocked(...)` (today's transaction, which yields survey_id_conflict for a foreign id). If a body needs a parcel lookup the CTE cannot express (parcel resolved from coordinates through the cadastre provider), that operation goes straight to upsertLocked; count such ops in the SUMMARY (the budget cases send parcel ids).
3. Update path (newer sync_version, not submitted), statement B: `updateSurveyIfUnchanged(db, input, casToken)` = one CTE: `ensured` parcels → `u` (`UPDATE surveys SET … WHERE id = $1 AND user_id = $2 AND xmin = $token::xid AND sync_version < $n AND status <> 'submitted' RETURNING id, updated_at::text`) → `d` (`DELETE FROM survey_parcels WHERE survey_id IN (SELECT id FROM u) AND parcel_id <> ALL($ids::text[])`) → `i` (`INSERT INTO survey_parcels SELECT u.id, x FROM u, unnest($ids::text[]) x ON CONFLICT (survey_id, parcel_id) DO NOTHING`) → `ev` ("updated" event from u) → `SELECT * FROM u`. Never DELETE-all plus INSERT of overlapping keys in one CTE (same snapshot; RESEARCH anti-pattern). 0 rows → upsertLocked. Why xmin: submitSurvey and applyVisibilityChange change the row without bumping sync_version (RESEARCH Pitfall 6).
4. Same-version identical replay: statement A only. Visibility-only same-version: keep today's applyVisibilityChange transaction.
5. Errors (including the fault-injection trigger making the event INSERT raise) propagate; they never route to upsertLocked (C-5). A single statement is atomic, so nothing commits.
6. Other op types (delete, visibility, attachments), patch, submit and REST paths other than upsert keep their transactions unchanged.
Budget targets (100 ops + 1 auth lookup): creates ≈ 201, updates ≈ 201; limits floor(1001/3) = 333, floor(901/3) = 300, floor(1301/3) = 433, floor(1101/3) = 367.
